# 서버 장애 대응 추정 시뮬레이션

서버 계산(`/api/judge`, `/api/plans`, `/api/sensitivity`, `/api/report`)을 쓸 수 없을 때 브라우저가 대신 계산하는 기능의 규칙과 한계를 적는다. 서버가 정상이면 이 코드는 쓰이지 않는다.

- 계산: `src/api/estimatePlans.ts` · 장애 판단: `src/api/fallback.ts` · 스냅샷: `src/api/snapshot.ts` · 상태: `src/store.ts`의 `run()`
- 추정 코드는 서버 코드를 가져다 쓰지 않는다. 아래 규칙은 공개 API 응답, 레포트 각주, 서버 규칙을 옮긴 About 화면에서 확인한 것이다.

## 1. 언제 쓰나

| 실패 | 처리 |
|---|---|
| 연결 실패, 시간 초과, 5xx, 읽을 수 없거나 형식이 틀린 응답 | 복구 가능한 장애: 추정으로 넘어간다 |
| 400 같은 입력 오류, 404, 429 | 오류를 그대로 보여 준다. 추정으로 숨기지 않는다 |
| 부른 쪽이 취소한 요청 | 무시한다(더 새 요청이 있다) |

- 판정 · 대안 · 지역 자료의 장애를 따로 기억한다. 대안 API만 실패하면 판정은 서버 값을 쓴다.
- 실패한 뒤 60초 동안은 서버를 다시 부르지 않고 바로 추정한다. 그 뒤에는 추정 값을 먼저 보여 주고 뒤에서 서버를 한 번 묻는다. 되면 서버 값으로 바꾼다.
- 결과에는 `source: 'server' | 'estimated'`가 붙는다(`Load<T>`). 민감도는 대안과 출처를 맞추고, What-if는 표 전체를 한 출처로만 계산한다.

## 2. 상황별 동작

| 상황 | 동작 |
|---|---|
| 마을 자료를 이미 받았고 계산 API 실패(상황 A) | 판정 · 대안 · 민감도 · What-if를 추정한다. 레포트는 추정 요약으로 대신한다. 실제 최적화 결과가 아니며 서버보다 달성률이 높거나 낮을 수 있고 목표 달성 여부도 다를 수 있다고 화면에 항상 표시한다 |
| 서버 전체 장애(상황 B) | 정적 스냅샷이 있으면 그 자료로 같은 추정을 한다([offline-snapshot.md](offline-snapshot.md)). 없으면 진단과 계산을 할 수 없다고 안내하고 다시 시도를 준다. 숫자를 만들지 않는다. 지금 배포는 스냅샷이 없다(6절) |
| 자료는 있는데 추정할 수 없음(이 나이대 주민 0명, 잘못된 값) | 원인을 알리고 다시 시도를 준다 |

샘플 데이터로 만든 데모 모드는 만들지 않았다. 실제 자료 스냅샷으로 흐름을 이어 갈 수 있고, 가짜 숫자가 실제 지역처럼 보일 위험이 있어서다.

## 3. 계산 규칙

입력은 화면의 현재 `State`와 `RegionData`다. 예산 · 인구 · 단가를 상수로 박지 않는다.

**기준 판정**: `judgeLocal(data, {service: 'med', age, criteria}, 'med')`. 진단 화면의 자가용 탭과 시설 필터는 들어오지 않는다. 서버 `/api/plans`는 `service`와 상관없이 병원 가는 길 판정에서 출발하므로 추정도 그렇게 한다(서버 응답으로 확인: `service=bus`여도 기본 달성률이 같다). 주민이 0명이면 추정하지 않는다.

**공급수단** (서버 응답으로 확인한 규칙)

| 수단 | 후보 | 닿는 범위 | coverage |
|---|---|---|---|
| `fix` 보건진료소 신설 | 공백 마을 | 그 마을과, 새 진료소까지 자가용 기준 안이면서 버스로 갈 수 있는 '너무 먼'(state 2) 마을. 거리는 아래 도로 시간 상한으로 잰다 | 1 |
| `drt` 수요응답형 버스 | 버스가 없어 못 가는 마을이 있는 읍면 | 그 읍면의 state 1 마을만. 자가용으로도 먼 state 2 마을은 그대로 | 1 |
| `tour` 순회 진료 버스 | 공백 마을(state 1 · 2). 주 2회 이상일 때만 | 정차한 마을만, 한 대 8곳까지 | 1 |
| `tele` 경로당 원격진료 | 경로당이 있는 공백 마을 | 그 마을만 | `teleEffect` |

한 마을의 coverage는 수단별 값 중 큰 값이다. 다른 수단으로 닿은 마을에는 원격진료를 놓지 않는다.

**순회 노선**: 프론트에는 마을 사이 도로 시간이 없다. 직선거리는 쓰지 않고, 서버가 준 '마을 → 시설' 도로 시간(가까운 병의원, 종류별 시설, 응급의료기관)을 이어 그래프를 만들고 최단 경로를 구한다. 시설을 거쳐 가는 길도 실제 길이므로 진짜 도로 시간은 이 값을 넘지 않는다(**상한**, 양방향 시간은 같다고 본다). 마을 안 시설은 그 마을과 같은 자리로 본다. 상한으로 잰 왕복이 레포트 각주의 기준 165분 안인 구간만 잇는다.

- 이어지지 않거나 왕복 상한이 165분을 넘는 마을은 정차에서 빼고 화면에 곳 수를 알린다.
- 상한이라 실제보다 길게 잡혀, 서버가 닿는 외곽 마을을 추정은 못 닿는다고 볼 수 있다. 도로 사정, 정차 시간, 버스 속도는 보지 않는다.
- 이 상한이 실제 도로 시간을 넘지 않는지는 마을 사이 실측값이 없어 직접 검증하지 못했다. 양방향 시간이 같다는 가정과 마을 안 시설을 같은 자리로 보는 단순화가 들어 있다.
- 처음에는 시설 하나만 거치는 상한을 썼는데 내륙 군에서 최대 19.4%p까지 과소 추정해 그래프 방식으로 바꿨다(최대 1.2%p). 보정 상수는 넣지 않았다.
- 지도의 노선은 기존과 같이 정류장 사이 직선이다.

**비용**: 수단 연 비용 = 설치비 ÷ 기간 + 운영비. 안의 연 비용은 합계이고, 예산 제약은 연 비용에 건다. 설치비 합계는 따로 보여 준다.

**달성률**: `(원래 갈 수 있는 주민 + Σ 공백 마을 주민 × coverage) ÷ 전체 주민`. 표시용 달성률은 소수 4자리로 반올림하고, 목표 달성 여부는 반올림 전 값으로 판단한다.

**10년 뒤**: 80세 이상일 때만 `Σ(a80 × a80In10y × coverage) ÷ Σ(a80 × a80In10y)`. 서버 값과 소수 4자리까지 일치함을 확인했다. 나머지 나이대는 `null`.

## 4. 대안을 찾는 방법

서버는 CP-SAT 최적화를 쓰고, 추정은 결정적 근사를 쓴다. 전역 최적이라고 주장하지 않는다.

1. 수단별 수량 조합(`fix`, `tour`, `drt`)을 나열한다. 수량 16까지는 하나씩, 넘으면 간격을 넓힌다(예산과 무관한 값).
2. 조합마다 새로 닿는 주민이 가장 많은 것부터 배치하고, 마지막에 원격진료를 주민 많은 순으로 채운다.
3. 세 안을 고른다.

| k | 안 | 고르는 기준 |
|---|---|---|
| 0 | 비용 절감안 | 예산 안에서 목표를 채우는 가장 싼 조합. 못 채우면 가장 많이 닿는 조합 |
| 1 | 균형안 | 위와 같되 원격진료 제외 |
| 2 | 적극 투자안 | 예산 안에서 가장 많이 닿는 조합, 같으면 싼 조합 |

- 추천: 균형안이 목표를 채우면 균형안 → 비용 절감안이 채우면 비용 절감안 → 달성률이 가장 높은 안(같으면 앞 번호).
- 동률은 비용 → 배치 수 → 먼저 찾은 순서로 정해 입력이 같으면 결과도 같다.
- 조합 후보가 예산과 무관해 예산이 늘면 후보가 늘기만 한다. 그래서 예산을 늘려 적극 투자안 달성률이 떨어지는 일이 없다.
- `sameAs`는 이름이 아니라 실제 배치를 비교한다. `timedOut`은 항상 `false`다(근사임은 출처 표시로 알린다).
- 민감도는 단가를 ±20% 바꿔 처음부터 다시 계산한다.

**추천 불일치 원인**

- 순회 단독 2곳(봉화군, 하동군): 각각 외곽 마을 1곳(석포면 승부리 17명, 악양면 중대리 24명)의 왕복 상한이 165분을 넘어 정차에서 빠졌다. 달성률 99.56% · 99.55%로 목표 100%에 못 미쳐 추천이 균형안에서 비용 절감안으로 넘어갔다. 세 안의 배치는 같아 실제 내용 차이는 그 마을 1곳이다. 원인 마을을 응답 비교로 확인했다.
- 다양한 조건 9건: 추정 균형안(원격 제외)이 목표를 채우고 서버 균형안은 못 채운 경우 7건(양평군 2, 예천군 2, 청양군, 거창군, 창녕군), 목표 99~100%에서 추정 균형안이 못 채운 경우 2건(고흥군, 순창군).

**오차의 원인**

- 서버는 조합 전체를 최적화하고 추정은 탐욕 배치라 서로 다른 조합을 고른다. 수단 구성까지 같은 비율은 비용 절감 494 · 균형 526 · 적극 투자 274 (각 648건 중)다. 달성률이 비슷해도 배치는 다른 경우가 많다.
- 순회 노선: 추정이 높은 354건 중 335건에 순회가 들어 있다. 서버 노선은 후보에서 고르느라 정차가 많이 겹치는데(예: 창녕군 순회 단독 11대 중 뒤쪽 노선은 새 마을 1~4곳) 추정 노선은 겹치지 않는다. 이것이 주된 원인으로 보이지만, 서버 노선 생성 규칙이 공개되지 않아 **단정하지 못한다**. 서버에 없는 제약 때문에 추정 노선이 실제로는 불가능할 가능성을 배제하지 못한다.
- 순회가 없는데 추정이 높은 19건: DRT · 원격진료는 단독 조건에서 서버와 값이 정확히 같아 규칙을 안다. 상위 사례에서 서버가 `timedOut`(시간 제한 내 최선)이었으므로 서버가 최적을 찾지 못한 경우로 보인다. 표본 전체에서 서버 `timedOut`은 171/1,944건이다.
- 추정이 낮은 경우: 도로 시간 상한이 실제보다 길어 외곽 마을이나 많은 정차를 잇지 못한다.
- 공백 인구 0명 마을은 추정에서 정차 · 배치하지 않는다. 비용에 영향이 없으면 서버는 놓기도 한다.

**비교하지 않은 것**: 단가 민감도 값과 레포트 내용은 추정과 서버를 비교하지 않았다(추정 레포트가 없고, 민감도는 서버와 대조 없이 규칙과 단위 테스트로만 확인했다). 서버 응답 자체가 옳은지는 검증 대상이 아니다.

## 6. 스냅샷

정적 자료 59개 지역을 배포에 포함한다. 나머지 13개 지역은 서버 정상 때만 쓴다. 공개 범위와 조건은 [data-licenses.md](data-licenses.md), 구조는 [offline-snapshot.md](offline-snapshot.md)에 있다.

## 7. 알려진 한계

- 정적 자료에 없는 13개 지역은 서버 전체 장애 때 쓸 수 없다.
- 정밀 판정의 첫차 추정값 등 원자료의 한계는 서버와 같다(`docs/data-audit.md`).
- 서버가 있어도 추정 중에는 마을 카드(`/api/village`)와 AI 질문(`/api/ask`)을 먼저 서버에 묻는다. 연결이 안 되면 마을 카드는 원자료로 계산하고, 질문 창은 자료 조회로 바뀐다.
- 결과 화면의 지도는 대안 번호(k)가 바뀌거나, 추정과 서버 사이를 오가며 배치가 달라질 때만 다시 맞춘다. 같은 출처에서 조건만 바뀌어 배치가 달라지면 지도는 따라 움직이지 않는다. 기존 동작이다.

## 8. 페이지를 떠날 때 요청 끊기

서버가 응답 없이 멈춘 상태에서 주소 입력 · 링크로 페이지를 떠나면, 브라우저가 페이지를 뒤로 가기 캐시에 얼리면서 멈춘 요청을 살려 둔다. 그러면 서버가 돌아와도 같은 주소의 새 요청이 막혀 첫 재시도가 20초 뒤 실패했다.

- 원인: HTTP/2(운영)에서는 크롬 HTTP 캐시 잠금(같은 주소 20,054ms, 캐시를 안 쓰면 50ms, 다른 주소 14ms). HTTP/1.1에서는 호스트당 연결 한도도 겹친다. 새로 고침에서는 생기지 않는다.
- 조치: `src/api/client.ts`가 `pagehide`에서 가는 중인 요청을 끊는다(HTTP/1.1 · HTTP/2 각 4개 흐름에서 첫 재시도 0.5초). 요청 없이 떠난 페이지는 뒤로 가기 캐시에서 그대로 복원한다.
- 대가: 요청 중에 떠났다가 뒤로 돌아오면 페이지를 새로 불러오므로 화면에서 바꾼 조건이 처음으로 돌아간다.
- `/api/ask`(AI 질문)는 자체 요청을 써서 이 처리에 들어가지 않는다.
